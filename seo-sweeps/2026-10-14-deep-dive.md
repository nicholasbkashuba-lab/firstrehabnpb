## What failed

There were two separate blockers. Fixing only the first will not be enough.

### 1. No service-account key in this run's environment

```
$ python3 tools/gsc.py verify
gsc: no service-account credentials found.
  Set GSC_SERVICE_ACCOUNT_JSON, pass --key <path>, or place the key at
  ~/.config/gsc/service-account.json
```

- `$GSC_SERVICE_ACCOUNT_JSON` was unset.
- `~/.config/gsc/` did not exist.
- No `*service-account*.json` anywhere on the filesystem.

The weekly SEO sweep (2026-10-12) did get GSC numbers, so the key exists somewhere. It lives
in that routine's cloud-environment setup script, which this routine's environment does not
share. A routine only gets the key if its own environment writes it.

### 2. The egress proxy blocks the Google API hosts

Even with a key, the calls would fail. In this environment the proxy refused the CONNECT for all
three hosts `gsc.py` uses:

| host | used for | result |
|---|---|---|
| `oauth2.googleapis.com` | token exchange (`TOKEN_URL`) | rejected by the proxy |
| `searchconsole.googleapis.com` | every query (`API`) | `connect_rejected`, 403 |
| `www.googleapis.com` | scope host | rejected by the proxy |

CLAUDE.md says "Google API hosts ARE reachable from the sandbox". That was true for the
environment the weekly sweep uses. It is **not** true for this one, so the network allow-list
differs between environments as well as the secrets.

### 3. Minor: `gsc.py sites` does not exist

The brief and CLAUDE.md both say to run `python3 tools/gsc.py sites`. On this branch (and on
`main`) the CLI accepts only `verify / summary / queries / pages / compare / raw`, so `sites`
exits with `invalid choice`. `verify` is the command that lists the properties the key can see
(it calls `/sites`). Either add a `sites` alias or change the two docs to say `verify`.
